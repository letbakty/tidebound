## SIM-01 🔴 Очки снимаются до того, как вода поднимется — «испытание сизигии» не работает

**Где:** `sim/run_state.gd:161–169` (`on_phase_started`), `sim/sim_world.gd:189–207` (порядок в тике).

**Что происходит.** Снимок очков делается в `on_phase_started(HIGH)`:
```gdscript
func on_phase_started(phase: int, w: SimWorld) -> void:
	if finished or phase != int(SimTypes.Phase.HIGH) or w.clock.cycle < ship_cycle:
		return
	...
	score_snapshot = compute_score(w)          # <-- строка 169
```
В `SimWorld.tick()` обработчики `phase_changed` вызываются **до** `tide.update(clock)`. То есть на этом тике `tide.level` ещё равен уровню конца Сигнала — **−6.0**. Даже после `tide.update` было бы −6.0: `tick_in_phase` только что обнулился, а кривая HIGH начинается ровно с `SIGNAL_LEVEL`.

`compute_score` отбрасывает только затопленные склады:
```gdscript
if Balance.is_mark_flooded(Balance.cell_to_mark(s["cell"]), w.tide.level):
	continue
```
При уровне −6 затоплены только склады на −7 и −8. Всё остальное считается.

**Почему это важно.** `docs/00-functional-spec.md:294` формулирует это как ключевую механику финала:
> «цикл 12 — Сизигия (вода +2), поэтому склады на +1..+2 **в этот момент под водой** — финальное испытание забега: ценное надо заранее поднять на ≥+3»

Сейчас поднимать ничего не надо: к моменту снимка вода на минимуме фазы. Вся стратегическая надстройка последнего цикла (и подсказка HintCard, запланированная на этап 15) теряет смысл. Комментарий в самом коде описывает правильное намерение — реализация ему противоречит.

**Почему тест это пропускает.** `tests/test_save.gd:123` (`test_flooded_storage_scores_nothing`) форсирует уровень через `w.tide.level_override = 0.0` и проверяет только «под водой груз не считается». Реальный момент снимка не проверяется ни одним тестом.

**Как проверить.** Прогнать забег до 12-го цикла и напечатать `w.tide.level` в момент `ship_arrived`. Ожидается −6.0.

**Куда смотреть при починке.** Либо снимать очки на пике HIGH (`tick_in_phase >= Balance.HIGH_RISE_TICKS`), либо в конце HIGH, но по уровню плато, а не по текущему. Второе ближе к докам («в момент прибытия»), первое — к формулировке «на Высокой». Решение должно быть записано в docs, потому что от него зависит весь баланс последнего цикла.

## SIM-02 🔴 Снос недостроенной постройки создаёт ресурсы из воздуха

**Где:** `sim/building_system.gd:452` (`demolish`) → `:460` (`_destroy`).

**Что происходит.**
```gdscript
func _destroy(b: Dictionary, w: SimWorld, refund_fraction: int) -> void:
	if refund_fraction > 0:
		for k in keys:
			var n: int = int(d.cost[k]) / refund_fraction   # 50% стоимости
			... drop(...)
	# затем отдельно возвращается ВЕСЬ буфер
```
Материалы списываются из буфера **только при завершении стройки** (`advance_construction`, строка «Тратим ровно стоимость»). Значит:

| Состояние постройки | Стоимость потрачена? | Что вернёт снос |
|---|---|---|
| `PLANNED` (материалы ещё не привезли) | нет | **50% стоимости из ниоткуда** |
| `PLANNED` (буфер полон) | нет | буфер + **ещё 50% из ниоткуда** |
| `UNDER_CONSTRUCTION` | нет | буфер + **ещё 50% из ниоткуда** |
| `ACTIVE` | да | 50% — корректно |

**Эксплойт в одну кнопку:** поставить Горн (6 утиля) → сразу снести → получить 3 утиля на землю. Повторять. Экономика забега ломается полностью.

**Почему тест это пропускает.** `tests/test_buildings.gd:218` ставит постройку через `place(..., instant = true)`, то есть сразу `ACTIVE` — единственный случай, где возврат корректен.

**Куда смотреть.** Возврат должен зависеть от состояния: `refund = (state == ACTIVE) ? cost/2 : 0`. Буфер возвращается всегда — это уже правильно.

## SIM-03 🔴 Лебёдка сушит мокрое и обнуляет порчу

**Где:** `sim/production_system.gd:153` (`_output`), вызов из `:200` (`_tick_winch`).

**Что происходит.** `_output` пересоздаёт стак с нуля:
```gdscript
var stack: Dictionary = StackUtil.make(item_id, n, false)   # wet = false, spoil_left = def.spoil_cycles
```
Для настоящего производства это верно (выход рецепта — свежий и сухой). Но лебёдка зовёт ту же функцию, пробрасывая только `item_id` и `count`:
```gdscript
_output(b, str(first["item_id"]), int(first["count"]), w)
```
Итог: положенный в корзину **мокрый плавник поднимается сухим**, а **сырая добыча со `spoil_left = 1` поднимается со `spoil_left = 3`**.

**Почему это важно.**
- Сушила и весь цикл сушки (`DRY_CYCLES`, `DRY_MIN_MARK`, топливо очага только сухим плавником) обесцениваются: лебёдка сушит бесплатно и мгновенно.
- Порча (`spoil_cycles` у `catch` = 3, у `rations` = 12) обходится: достаточно раз за цикл прогонять еду через корзину.

**Побочный эффект той же строки.** Поднятый груз попадает в `_produced_cycle`, то есть в отчёт цикла как «произведено». Перенесённое считается изготовленным — статистика в итогах и будущий баланс-CSV искажены.

**Куда смотреть.** Лебёдке нужен путь, сохраняющий стак целиком (`store`/`drop` исходного словаря), а не `_output`. Либо `_output` должен принимать готовый стак, а не `(item_id, n)`.

## SIM-04 🟠 Скорость игры сбрасывается на ×1 после каждого цикла

**Где:** `autoload/game.gd:320` и `:368` (две записи в `_paused_speed`), `:135` (`resume_prev_speed`).

**Что происходит.** На границе цикла в одном тике эмитятся `cycle_ended`, `cycle_started` и (через `run_state`) `draft_ready`. В `_flush_events` обе ветки пишут в один и тот же `_paused_speed`:
```gdscript
"cycle_ended":
	_paused_speed = speed          # запомнили ×3
	cmd_set_speed(0)
...
"draft_ready":
	_paused_speed = speed          # speed уже 0 -> запомнили 0
	cmd_set_speed(0)
```
Затем `resume_prev_speed()` делает `cmd_set_speed(maxi(1, _paused_speed))` → **×1**.

**Что видит игрок.** Каждый цикл выбранная скорость ×2/×3 молча падает до ×1. На 12 циклов это 11 раз.

**Куда смотреть.** Запоминать прежнюю скорость только при переходе из ненулевой в нулевую (`if speed != 0: _paused_speed = speed`), либо ввести счётчик глубины паузы — он всё равно понадобится этапу 15 (наложение Итога цикла и Драфта), см. `research/21 §5`.

## SIM-05 🟠 Существо проходит сквозь закрытый шлюз при двух лестницах на ярус

**Где:** `sim/crisis_system.gd:317–322` (`_move_towards`), `sim/terrain.gd` (`_rebuild_graph`, `rebuild_wet_graph`).

**Что происходит.** Граф связывает **отметки**, а не отдельные лестницы: любая лестница с `mark_top = M` создаёт одно и то же ребро `M ↔ M−1`. Шлюз блокирует ребро по `ladder_id`, но если между теми же ярусами стоит вторая лестница, ребро всё равно существует.

Дальше существо выбирает колонку для спуска так:
```gdscript
for l: Dictionary in w.terrain.ladders:
	if int(l["mark_top"]) == top:
		lx = int(l["x"])
		break                       # первая попавшаяся, блокировка не проверяется
```
То есть оно может физически спуститься **по той самой лестнице, на которой стоит шлюз**.

**Что видит игрок.** Построил шлюз на лестнице — существо прошло сквозь него. Контр-игра из docs §9.3 («Шлюз перекрывает рёбра графа») перестаёт быть надёжной, а причина невидима.

**Смежное.** Шлюз ищется как `ladder_id_at(gate.cell.x, gate.mark)` — то есть должен стоять **ровно** в колонке лестницы и на её верхней отметке. Промах на клетку = шлюз не работает, и никакого сигнала об этом нет.

**Куда смотреть.** Либо ребро на лестницу (а не на пару отметок), либо в `_move_towards` выбирать только незаблокированную колонку, либо блокировать все лестницы яруса, если шлюз стоит хоть на одной. Первое честнее и снимает вопрос навсегда, но трогает `find_path` у агентов.

## SIM-06 🟠 Существа не вызывают панику у Пугливых

**Где:** `sim/agent_system.gd:195–196` (комментарий «Этап 09 добавит сюда…» остался невыполненным), `sim/crisis_system.gd:344`.

**Что происходит.** `_check_panic` учитывает только `mood < 30` и положение ниже опасной отметки. Существа влияют лишь на настроение (`_scare_agents`, −10 один раз за цикл). Модификатор `panic_range` (черта Пугливый, 8 тайлов) используется **только** как радиус испуга, а не как триггер состояния `PANIC`.

**Спека:** `docs/00 §9.3` — «агент в 4 тайлах — Дух −10, **паника у Пугливых**». Промпт 09 то же: «Пугливый — паника с 8 тайлов».

**Следствие.** Черта Пугливый почти бесполезна: −10 духа получают все, а обещанное отличие не реализовано. Заодно исчезает единственный способ «косвенной смерти от существ», описанный в docs («паника → не успел уйти от воды»).

## SIM-07 🟠 Сломанные штормом лестницы полностью останавливают колонию

**Где:** `sim/terrain.gd` (`nearest_ladder_dist` возвращает `INF`), `sim/job_system.gd` (`_greed_allows`).

**Что происходит.** Фильтр Жадности:
```gdscript
return w.terrain.nearest_ladder_dist(j["cell"]) <= float(limit)
```
`nearest_ladder_dist` при отсутствии лестниц возвращает `INF`. `INF <= 4` → `false`. При Жадности 0–2 **все** задачи на отметках ниже 0 отфильтровываются.

**Сценарий.** Шторм 10-го цикла ломает деревянные лестницы ниже +3. Пока их не починят, колония не берёт ни одной задачи на дне — но задачи REPAIR (они на самих лестницах, отметка ≤ 0) тоже отфильтрованы тем же правилом. ⚠️ **Не подтверждено:** зависит от того, попадает ли клетка сломанной лестницы под `Balance.cell_to_mark(...) >= 0`; для лестниц ниже нуля — попадает под фильтр.

**Почему это важно.** Возможен «мёртвый замок»: чинить нельзя, потому что нет лестниц; лестниц нет, потому что не чинят. Игрок увидит бездействующую колонию без объяснения.

**Куда смотреть.** Исключить классы `BUILD`/`REPAIR` из фильтра Жадности (он про риск добычи, а не про стройку), либо считать `nearest_ladder_dist` до цели с учётом того, что сама цель и есть лестница.

## SIM-08 🟡 Мокрый флаг агента снимается сам на границе цикла

**Где:** `sim/agent_system.gd` (`on_cycle_started`): `a.wet = false` с комментарием «к началу нового цикла успел обсохнуть».

**Что происходит.** Механика сушки у очага (`WET_DRY_SEC_AT_HEAT = 30 с`, `heat_ticks`) существует, но её результат почти всегда достигается бесплатно: агент мокнет во время Отлива/Сигнала и автоматически сохнет на границе цикла.

**Следствие.** Разница между `WARMTH_PER_CYCLE_MILLI` (−10) и `WARMTH_WET_PER_CYCLE_MILLI` (−25) действует лишь до конца текущего цикла, а очаг как «сушилка для людей» почти не нужен. Это ослабляет и роль топлива, и черту Мерзляк.

⚠️ Возможно, это осознанное решение (комментарий это утверждает) — но оно нигде не зафиксировано в docs и делает часть чисел §6.3 декоративными.

## SIM-09 🟡 Испаритель: флаг «был затоплен» сбрасывается на каждой фазе

**Где:** `sim/building_system.gd:192` (`on_phase_started`), `sim/production_system.gd` (`_passive_allowed`).

**Что происходит.**
```gdscript
func on_phase_started(_phase: int) -> void:
	for id in order:
		buildings[id]["flooded_in_phase"] = bool(buildings[id]["flooded"])
```
Сброс идёт на **каждой** смене фазы, а испарителю нужен признак «был ли затоплен за всю фазу LOW». Порядок в `SimWorld.tick`: `production.on_phase_ended(prev)` вызывается **до** `buildings.on_phase_started(phase)`, поэтому соль считается по правильному флагу.

Но связь неявная и держится только на порядке двух строк в `sim_world.gd`. Любая перестановка обработчиков `phase_changed` тихо сломает правило «испаритель не даёт соль в цикл, в середине которого его накрыло», и ни один тест этого не покажет (`test_evaporator_needs_dry_low` проверяет результат, а не устойчивость к порядку).

## SIM-10 🟡 Автопауза не останавливает тик немедленно

**Где:** `autoload/game.gd:36–48` (`_physics_process`).

**Что происходит.** `speed` проверяется один раз на входе в функцию; `cmd_set_speed(0)` из `_flush_events` не прерывает `while`-цикл. При ×3 и накопленном `_accum` после конца цикла может пройти ещё до 11 тиков.

**Следствие.** Драфт и Итог цикла показываются на состоянии, которое на секунду «убежало» вперёд. Для этапа 15 (панель Итога цикла) это значит, что цифры отчёта и состояние мира на экране могут не совпадать.

## SIM-11 🔵 `_nearest_storage` считает «путь длиной 0» признаком отсутствия пути

**Где:** `sim/agent_system.gd` (`_nearest_storage`).

```gdscript
if pid != a.platform_id and is_equal_approx(d, 0.0):
	continue                                  # пути нет
```
`find_path` возвращает пустой массив, `path_length_tiles([])` даёт 0.0 — отсюда трюк. Он работает, но связывает два несвязанных понятия. Достаточно проверить `find_path(...).is_empty()` напрямую — тем более что путь уже посчитан строкой выше.

## SIM-12 🔵 `SimWorld.replay` затеняет встроенную функцию `log()`

**Где:** `sim/sim_world.gd` — `static func replay(seed_value: int, log: Array[Dictionary], ...)`.

`log` — глобальная математическая функция GDScript. Параметр её затеняет; движок выдаёт предупреждение `shadowed_global_identifier`, и внутри функции `log(x)` перестаёт работать. Достаточно `cmd_log` или `entries`.
