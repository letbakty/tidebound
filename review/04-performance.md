# 04 — Производительность

Масштаб проекта крошечный (6–12 агентов, ~15 узлов графа, 10 тиков/с), поэтому большинство найденного — **не проблема сегодня**. Выделено то, что либо уже стоит дорого на кадр, либо станет дорогим при росте (16 агентов к релизу, второй/третий утёс).

Бюджет из `docs/00 §16`: **≤ 2 мс на тик**. Инструмент уже есть — `Game.tick_budget_ms()` и график в дебаг-панели. ⚠️ Замеров не проводилось: ниже — анализ кода, а не профилирование.

---

## PERF-01 🟠 `AgentView` дёргает полный срез агента 60 раз в секунду

**Где:** `game/agent_view.gd` — `_process` → `_refresh_look` → `Game.query_agent(agent_id)`.

Каждый кадр на каждого агента:
```gdscript
return {
	...
	"traits": a.trait_ids.duplicate(),
	"bag": a.bag.duplicate(true),        # ГЛУБОКАЯ копия всех стаков котомки
	...
}
```
плюс `world.agents.agent(id)` — линейный поиск ([ARCH-09](03-architecture-risks.md#arch-09)).

При 6 агентах это ~360 словарей и ~360 глубоких копий котомок в секунду. При 12 — вдвое больше. И всё это ради трёх полей: `state`, `wet`, `facing`.

**Что стоит сделать.** Отдельный лёгкий `Game.query_agent_look(id) -> {state, wet, facing}` без копий, а полный `query_agent` оставить карточке агента (этап 14), которая опрашивает раз в секунду. Это ровно то разделение «view-model для кадра» / «view-model для панели», о котором говорит `research/25 §2.3`.

## PERF-02 🟡 `StorageSystem.drain_events` пересчитывает агрегат каждый тик

**Где:** `sim/storage_system.gd` — `drain_events()` вызывает `totals()`.

`totals()` обходит все склады и все стаки, строит словарь, затем **второй** словарь для сортировки, и вызывает `DB.item_ids()`, который каждый раз собирает и **сортирует** массив из 13 строк. Это 10 раз в секунду при том, что склады меняются в разы реже.

**Что стоит сделать.** Пересчитывать только по флагу «склады менялись в этом тике» — флаг уже фактически есть (`_pending` непуст), достаточно им воспользоваться. Плюс закэшировать `DB.item_ids()` (список неизменен после загрузки).

---

## PERF-03 🟡 `_has_job_for` делает генерацию задач квадратичной

**Где:** `sim/job_system.gd` — `_has_job_for(kind, target_id)` перебирает весь пул для **каждого** кандидата в `_generate_gather/_generate_haul/_generate_build/_generate_station/_generate_needs`.

При 10 депозитах, ~40 постройках и десятках предметов на земле это тысячи сравнений строк на каждую пересборку пула — а пересборка запускается по флагу `_dirty`, который взводится при каждом `pick_up`/`put_down` агента, то есть по нескольку раз за секунду.

**Что стоит сделать.** Индекс `Dictionary[String, int]` вида `"gather:12" → job_id`, обновляемый в `_make_job`/`cancel_haul`. Двадцать строк, и генерация становится линейной.

## PERF-04 🟡 Поиск по массивам вместо словарей в горячих местах

Одинаковый паттерн в нескольких системах:

| Функция | Файл | Частота |
|---|---|---|
| `storage_index(id)`, `storage_at(cell)` | `storage_system.gd` | из `take`/`store`/`count_in` — десятки раз за тик |
| `deposit_index(id)`, `deposit_at(cell)` | `terrain.gd` | на каждом тике добычи |
| `ladder_id_at`, `ladder_at` | `terrain.gd` | при проверке шлюзов и рисовании |
| `agent(id)` | `agent_system.gd` | см. PERF-01 |

Каждый — линейный проход. По отдельности незаметно; вместе это основная часть времени тика, если он когда-нибудь упрётся в бюджет. Лечится одинаково: словарь-индекс рядом с массивом, массив остаётся носителем порядка.

⚠️ **Не оптимизировать превентивно** — сначала замер (`docs/00 §16`, `research/26 §6.1`). Список приведён, чтобы знать, куда смотреть, когда график времени тика полезет вверх.

## PERF-05 🟡 Запись сейва внутри игрового цикла

**Где:** `autoload/game.gd` — ветка `"cycle_ended"` в `_flush_events` вызывает `SaveService.save_run(ui_state)`.

`_flush_events` вызывается **изнутри** `while`-цикла `_physics_process`. То есть дисковая запись (сериализация всего мира + `JSON.stringify` с `full_precision` + файловая операция) происходит в кадре физики.

Пока мир маленький, это единицы миллисекунд. Но:
- при `debug_fast_forward` (кнопка «+1 цикл») запись происходит на каждой границе — 12 записей за промотку забега;
- на мобильном хранилище это десятки миллисекунд и видимый фриз.

**Что стоит сделать.** Ставить флаг «нужен автосейв» и писать после выхода из цикла тиков — в конце `_physics_process` или в `_process`.

## PERF-06 🔵 Мир перерисовывает лестницы по опросу версии графа каждый кадр

**Где:** `game/world.gd` — `_process` каждый кадр сравнивает `t.graph_version != _drawn_graph_version`.

Сравнение целых чисел — бесплатно, но сам факт `_process` на корне мира ради одной проверки лишний: `graph_version` меняется только при событиях, которые уже эмитятся (`building_state_changed`, `building_removed`). Мелочь, но это тот же класс «опрос вместо события», который проект в других местах последовательно избегает.

---

## PERF-07 🔵 `Meta._process` крутится всегда ради одного bool

**Где:** `autoload/meta.gd` — `_process` проверяет `_dirty` каждый кадр всю игру.

`set_process(false)` + включение в `mark_dirty()` даёт то же поведение без вызова каждый кадр. Микро, но автолоад живёт всю сессию.

---

## PERF-08 💡 Что НЕ стоит оптимизировать

Чтобы не потратить этап впустую:

- **Пулы объектов для View.** Нод в мире — сотня; `research/15 §6.6` уже посчитал запас в 100×.
- **`Packed*Array` вместо `Array[int]`** в графе и путях. Массивы по 15 элементов.
- **Многопоточность.** Ломает детерминизм, ради которого построено всё ядро.
- **Инкрементальная перестройка AStar.** `_rebuild_graph` на 15 узлах дешевле любой инкрементальной логики и гарантирует одинаковый порядок рёбер — то есть детерминизм выбора пути. Это осознанно и правильно.
