# 30 — Методика балансировки: от soak-прогонов к кривой сложности

**Для этапов:** 05–11 (закладываются все числа), 19 (soak-тест — это уже заготовка данных), после 15 (первая настоящая балансировка).
**Дата ресерча:** 2026-08-21.

**Почему это Группа 1.** soak-тест из research/24 отвечает на вопрос «что сломалось». Он **не** отвечает на «слишком легко или слишком тяжело», «есть ли доминирующая стратегия», «какая политика бесполезна». Чтобы отвечать, нужны: (а) прогон **не одного, а множества сценариев поведения игрока**, (б) метрики, записанные заранее, (в) способ их читать. Всё три — про архитектуру, и всё три дешевле заложить на этапах 05–11, чем добавлять после.

## 1. Эталон: как это делают в играх нашей формы

Ближайший аналог — **Slay the Spire**: забеговая игра, рандом, решения игрока, метрики по каждому забегу. Их доклад GDC 2019 «Metrics Driven Design and Balance» — практический шаблон.

Что они делали и что переносится к нам:

| Их приём | Наш эквивалент |
|---|---|
| Метрик-сервер, пишущий **каждое решение** игрока | soak-CSV + лог команд (research/25 §2.1) — но **офлайн**, без сервера |
| «Как часто карту берут, когда предлагают» | как часто карта драфта выбирается ботом-стратегом |
| «Как часто карта встречается в **победных** колодах» | корреляция карты/политики с исходом SHIP |
| Внутренний Slack-канал с дайджестом метрик | CSV + одна страница графиков после каждого прогона |
| ⚠️ Их предупреждение: **метрики вводят в заблуждение, если читать их без интерпретации** | не оптимизировать «на автомате»: цифра указывает, где смотреть, а не что менять |

Второй полезный ориентир — академическая **Monte-Carlo simulation balancing**: параметры симуляции подкручиваются так, чтобы результат прогона приблизился к целевому распределению. Для нас важна не математика, а идея: **у баланса должна быть числовая цель, а не ощущение.**

⚠️ У нас нет игроков и телеметрии (её и не будет — ТЗ исключает телеметрию до фазы 2). Значит источник данных ровно один: **собственная симуляция, прогоняемая тысячи раз headless**. Это и сильная сторона — детерминизм и скорость, — и слабая: бот не играет как человек.

## 2. Ключевая идея: «стратегические профили» вместо одного автопилота

soak-тест research/24 гоняет **дефолтные политики**. Это одна точка в пространстве стратегий, и по ней нельзя сказать ничего о балансе.

**Профиль игрока** = фиксированный набор решений, которые в игре принимает человек:
- 6 значений политик,
- правило выбора карты драфта,
- правило постановки маяка,
- очередь построек,
- порог `leave_early`.

```gdscript
class_name StrategyProfile
extends RefCounted

var id: String = ""
var policies: Dictionary[int, int] = {}          # Policy -> 0..3
var build_order: Array[String] = []              # def_id по приоритету
var card_pref: Array[String] = []                # предпочтения драфта
var beacon_rule: String = "none"                 # "none"|"deepest"|"nearest_ruins"
var leave_early_at_cycle: int = -1               # -1 = не уходить

static func presets() -> Array[StrategyProfile]:
	return [
		_make("turtle",   {GREED: 0, CAUTION: 3, REPAIR: 2, BUILD: 2, SUPPLY: 2, REST: 2}),
		_make("greedy",   {GREED: 3, CAUTION: 0, REPAIR: 1, BUILD: 1, SUPPLY: 3, REST: 0}),
		_make("builder",  {GREED: 1, CAUTION: 2, REPAIR: 3, BUILD: 3, SUPPLY: 1, REST: 1}),
		_make("balanced", {GREED: 2, CAUTION: 2, REPAIR: 2, BUILD: 2, SUPPLY: 2, REST: 2}),
		_make("rusher",   {GREED: 3, CAUTION: 1, REPAIR: 0, BUILD: 3, SUPPLY: 2, REST: 1}),
	]
```

**Что это даёт:**
1. **Кривая сложности** = распределение очков по сидам для *каждого* профиля.
2. **Доминирующая стратегия** видна сразу: если `greedy` выигрывает на всех сидах с отрывом — жадность недоштрафована.
3. **Мёртвая механика** видна сразу: если `turtle` и `balanced` дают одинаковый результат — Осторожность ни на что не влияет.

⚠️ **Профиль — это НЕ ИИ.** Он не «играет хорошо», он играет **последовательно**. Именно постоянство делает сравнение осмысленным.

⚠️ **Профиль живёт в `tests/`, а не в `sim/`.** Он подаёт команды через тот же `world.apply_command`, что и игрок. Иначе появится второй путь исполнения, и баланс будет измеряться не в той игре, в которую играют.

## 3. Что заложить на этапах 05–11, чтобы это стало возможным

Всё дешёвое и ничего не нарушает «Не делать».

| Этап | Что | Зачем |
|---|---|---|
| **05** | счётчики в агенте: `ticks_by_state: Dictionary[int, int]`, `tiles_walked: float`, `items_gathered: int` | без них не понять, куда уходит время колонии |
| **06** | счётчики `JobSystem`: сколько задач каждого класса создано/взято/отменено/провалено | ловит «класс работ не берут никогда» |
| **07/08** | `buildings_built/lost`, `produced: {item: int}` за забег | цепочки производства |
| **09** | `crisis_damage`, `stolen`, `drowned` | цена кризисов |
| **11** | всё это — в `run_ended.report` (то же, что нужно достижениям, research/27 §2.3) | одна структура на три задачи |
| **11** | `RunState.timeline: Array[Dictionary]` — снапшот по циклам | **это и есть кривая внутри забега** |

**`timeline` — ключевая структура.** По одной записи на `cycle_ended`:
```gdscript
{
	"cycle": 5, "score_so_far": 180,
	"alive": 5, "avg_satiety": 62.3, "avg_warmth": 71.0, "avg_mood": 55.2,
	"totals": {"scrap": 24, "rations": 6, ...},
	"buildings_active": 9, "buildings_damaged": 1,
	"gathered": 31, "produced": 4, "lost_to_flood": 2,
	"deaths_this_cycle": 0,
	"ticks_by_state": {IDLE: 1200, GATHER: 8400, HAUL: 5100, ...},
}
```
⚠️ **Это ~15 чисел на цикл × 12 циклов = мелочь по объёму,** но именно они превращают «забег провалился» в «на 7-м цикле еда ушла в минус, потому что порча съедала быстрее, чем солильня производила».

⚠️ **`timeline` не обязан быть в сейве.** Он строится по ходу забега и нужен только отчёту и балансу. Если положить его в `to_dict`, сейв распухнет и хеш-тесты станут шумными. **Решение: держать отдельным полем, исключённым из сериализации** — записать комментарием, иначе следующий агент «починит».

## 4. Sweep-раннер

```gdscript
extends SceneTree
## tests/balance_sweep.gd
##   godot --headless -s res://tests/balance_sweep.gd -- --seeds=200 --out=docs/balance.csv
## Профили × сиды. 5 профилей × 200 сидов = 1000 забегов.

func _initialize() -> void:
	var args: Dictionary[String, String] = _parse_args(OS.get_cmdline_user_args())
	var seeds: int = int(args.get("seeds", "100"))
	var out_path: String = args.get("out", "res://../docs/balance.csv")

	var rows: PackedStringArray = [_header()]
	for profile: StrategyProfile in StrategyProfile.presets():
		for i: int in seeds:
			var seed_value: int = 100_000 + i * 7919
			rows.append(_run_one(profile, seed_value))
		print("%s: готово" % profile.id)
	FileAccess.open(out_path, FileAccess.WRITE).store_string("\n".join(rows))
	quit(0)

func _run_one(p: StrategyProfile, seed_value: int) -> String:
	var w := SimWorld.new()
	w.new_run(seed_value)
	for policy: int in p.policies:
		w.apply_command({"type": "set_policy", "policy": policy, "value": p.policies[policy]})
	var guard: int = 0
	while not w.run_state.is_over() and guard < 60_000:
		_profile_act(p, w)              # драфт, стройка, маяк, leave_early
		w.tick()
		w.events_out.clear()
		guard += 1
	var r: Dictionary = w.run_state.report()
	return _row(p, seed_value, r, w.run_state.timeline)
```

**Технические детали:**
- ⚠️ **`OS.get_cmdline_user_args()`** — аргументы **после `--`**. `OS.get_cmdline_args()` вернёт и флаги движка. Это единственный способ параметризовать headless-прогон.
- ⚠️ **Один seed на все профили.** Сравнивать профили можно только на **одинаковых мирах**: сид определяет карту, плавник, драфт, реликвии. Иначе разница в очках — это разница в сидах, а не в стратегиях.
- ⚠️ **Раздельные потоки RNG** (research/16 §4.1): `rng_world` и `rng_ai`. Без этого правка ИИ сдвинет генерацию мира, и все прошлые прогоны станут несравнимы. **Это причина завести два RNG на этапе 01, а не «на всякий случай».**
- **Время.** Забег = 36 000 тиков (12 циклов × 3000). При бюджете 2 мс/тик это 72 с — **неприемлемо для 1000 забегов**. Но 2 мс — это худший кадр с рендером; в headless тик стоит десятки микросекунд. Ориентир: **забег ≈ 1–3 с, 1000 забегов ≈ 20–50 минут**. Если дольше — гнать sweep ночью/в CI, а не в цикле правок.
- ⚠️ **Прогресс печатать.** Молчащий процесс на 40 минут неотличим от зависшего.

**Формат CSV — «широкий» по забегу + отдельный файл «длинный» по циклам:**
```csv
# docs/balance_runs.csv — по строке на забег
profile,seed,outcome,cycles,points,alive,deaths,drowned,relics,built,lost,cards
# docs/balance_timeline.csv — по строке на цикл
profile,seed,cycle,score,alive,avg_satiety,avg_warmth,avg_mood,gathered,produced,lost
```
Две таблицы, а не одна: иначе строки будут либо гигантскими, либо неудобными для группировки.

## 5. Что считать по CSV: пять вопросов и как на них отвечать

Анализ — обычным Python/pandas в `tools/analyze_balance.py`. ⚠️ **Не тащить графики в Godot** — это отдельная работа без пользы для игры.

### 5.1 «Игра проходима?»
`win_rate = доля outcome == SHIP` по каждому профилю.
**Целевой коридор для забеговой игры: 25–45% у среднего профиля.** Ниже — фрустрация, выше — нет напряжения.
⚠️ У нас бот играет **хуже** человека (он не адаптируется). Поэтому целиться в 15–30% у ботов и проверять на людях.

### 5.2 «Есть ли доминирующая стратегия?»
```python
piv = runs.pivot_table(index='seed', columns='profile', values='points')
# Насколько часто профиль лучший на своём сиде:
dominance = piv.idxmax(axis=1).value_counts(normalize=True)
```
⚠️ **Порог тревоги: один профиль лучший более чем в 50% сидов.** При 5 профилях случайность даёт 20%.
Дополнительно — **попарное сравнение на одинаковых сидах** (это сильнее среднего): `(piv['greedy'] > piv['turtle']).mean()`. Если 0.85 — жадность доминирует, штраф за риск слишком мал.

### 5.3 «Есть ли мёртвые механики?»
- **Мёртвая политика:** разброс очков при изменении только этой политики ≈ 0. Прогнать отдельный sweep «balanced, но политика X = 0..3» — 4 профиля, отличающиеся одним числом.
- **Мёртвая карта:** доля забегов, где выбранная карта коррелирует с исходом ≈ базовой.
- **Мёртвая постройка:** `built`-счётчик по def_id ≈ 0 у всех профилей → постройка не окупается либо недоступна.
- **Мёртвое состояние агента:** `ticks_by_state[IDLE] / total` высокий → колония простаивает, значит задач мало или скоринг их не находит (research/16).

⚠️ **«Мёртвая» ≠ «плохая».** Постройка может быть нишевой. Признак настоящей проблемы — **ноль применений во всех профилях на всех сидах**.

### 5.4 «Где ломается кривая?»
По `balance_timeline.csv`: средняя `score` и `alive` по циклу.
- **Резкий провал `alive` на конкретном цикле** → кризис этого цикла слишком силён (сизигия на 5-м, шторм на 9-м, Приход на 4/7/10).
- **`avg_satiety` монотонно падает** → цепочка еды не догоняет потребление; смотреть `produced.rations` против числа агентов.
- **`score` растёт линейно** → нет ускорения; экономика не «раскручивается», игра будет ощущаться плоской.
- **`score` растёт экспоненциально после 6-го цикла** → снежный ком; поздние циклы решают всё, ранние решения не важны.

### 5.5 «Натянуты ли цепочки?»
Специфика экономики TIDEBOUND: три цепочки (соль→рационы, металл→детали, водоросли→волокно) конкурируют за **время агентов** и **сухой плавник**.

```python
# Доля времени колонии по классам работ — «бюджет внимания»
t = timeline.groupby('profile')[['gather','haul','station','build','rest','idle']].mean()
```
⚠️ **Признак ненатянутой экономики: один ресурс всегда в избытке.** Если `scrap` к 12-му циклу лежит сотнями — утиль не является ограничением, и вся ветка металла бессмысленна. Лечится не «увеличить стоимость», а **уменьшить добычу или увеличить конкуренцию за время**.

⚠️ **Признак перетянутой: `idle` близок к нулю и `avg_mood` падает у всех профилей** — колония не успевает ничего, игрок не чувствует выбора.

## 6. Порядок работ (что делать после этапа 15)

1. **Зафиксировать целевые числа до прогонов.** Win-rate 15–30% у ботов, средняя длительность забега, доля смертей от утопления < X. Иначе данные будут «интерпретироваться» под желаемое.
2. **Прогнать baseline** (5 профилей × 200 сидов), сохранить CSV **в git с датой**. Это точка отсчёта.
3. **Менять по одному числу за раз** и перепрогонять. ⚠️ Две правки сразу — и нельзя сказать, какая сработала.
4. **Хранить историю прогонов** (`docs/balance/2026-08-21-baseline.csv`, `…-fix-greed.csv`). Регресс баланса ловится диффом так же, как регресс кода.
5. **Проверять на людях.** Бот не паникует, не забывает отозвать и не жадничает по-человечески. Метрики указывают, куда смотреть; решение — за плейтестом.

⚠️ **Не автоматизировать подбор параметров** (эволюционные алгоритмы, RL). Формально возможно, но: (а) целевая функция «интересно» не формализуется, (б) оптимизатор найдёт вырожденный оптимум, (в) это недели работы. Наш масштаб — ручная настройка по данным, как в Slay the Spire.

## Чек-лист

- [ ] `rng_world` и `rng_ai` разделены; правка скоринга не меняет карту при том же сиде.
- [ ] `run_ended.report` содержит все поля; ни одно не считается в UI повторно.
- [ ] `timeline` заполняется на каждом `cycle_ended` и **не попадает в сейв**.
- [ ] Sweep-раннер принимает `--seeds` и `--out` через `OS.get_cmdline_user_args()`.
- [ ] 5 профилей прогоняются на одних и тех же сидах.
- [ ] Baseline-CSV закоммичен с датой.
- [ ] Ни один профиль не выигрывает более чем в 50% сидов.
- [ ] Нет постройки/карты/политики с нулевым влиянием во всех профилях.
- [ ] Целевые числа записаны в `docs/` **до** первой правки баланса.
