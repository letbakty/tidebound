## 1. Дождь — шейдером, не частицами

Промпт называет дождь среди GPUParticles2D, но там же ограничивает «1–2 системы на экран». Полноэкранный ливень частицами требует тысяч частиц и съедает весь бюджет 30 fps на среднем Android.

**Решение:** дождь — полноэкранный `ColorRect` с процедурным шейдером. 1 draw call, 0 CPU. Освободившийся бюджет частиц уходит на то, ради чего частицы и нужны: **брызги** и **пар**.

### Где живёт

`ColorRect` 640×360 на `CanvasLayer` **внутри** WorldViewport (`layer = 5`, `follow_viewport_enabled = false`). Внутри — чтобы капли пикселизовались вместе с миром и попали под апскейл ×2/×3/×4. Дождь в нативном разрешении поверх пиксельного мира выглядит чужеродно.

### Ключевые приёмы в шейдере

1. **`discard` при `u_intensity <= 0.001`.** Оверлей висит в сцене все 12 циклов, но в ясную погоду не пишет ни одного пикселя. На тайловом мобильном GPU это заметная экономия.
2. **Два слоя с разной скоростью и масштабом** (`near_l`, `far_l * 0.55`) — дают ощущение глубины. Один слой читается как обои.
3. **Псевдослучайность по колонке** (`step(0.45, hash21(...))`) — иначе капли выстраиваются в решётку.
4. **`sim_time`, а не `TIME`** — дождь замирает на паузе вместе с миром.

Когда художник нарисует `rain_tile.png` 64×64 — заменить `hash21` на `texture(rain_tex, uv).r`. Объявление обязано нести фильтр явно:
```glsl
uniform sampler2D rain_tex : filter_nearest, repeat_enable;
```
Явный `filter_nearest` в объявлении переопределяет фильтр вьюпорта и гарантирует пиксельность независимо от `canvas_item_default_texture_filter`.

## 2. Виньетка — снаружи SubViewport, в нативном разрешении

Здесь важное решение, которое надо принять осознанно:

| Где | Вид | Вердикт |
|---|---|---|
| Внутри SubViewport (640×360) | градиент квантуется в 640×360 и апскейлится → крупные ступени и грязный бандинг | нет |
| Снаружи, поверх апскейла (нативное окно) | гладкий градиент в полном разрешении | **да** |

Виньетка — кинематографический эффект «объектива», а не часть пиксельного мира. Это согласуется с docs/01 §1.1: *«Screen-space шейдеры (вода, виньетка шторма): эффекты, которым нужна нативная чёткость, вешаются на SubViewportContainer или UI-слой»*.

Рекомендованное место: новый `WeatherLayer` (`CanvasLayer`, `layer = 25`) в `main.tscn`, между `PanelLayer` (20) и `BannerLayer` (30). Банер кризиса должен быть читаем поверх виньетки.

### Три обязательных условия

1. **Никакого `hint_screen_texture`.** Затемнение краёв не требует знать, что под ними — достаточно полупрозрачного градиента в `blend_mix`, экран просвечивает через blending. Второй screen-read шейдер вызвал бы вторую копию бэкбуфера, а на Mobile (тайловые GPU) это бьёт по пайплайну сильнее, чем сам эффект, и потребовал бы `BackBufferCopy`, что сломало бы воду.
2. **`render_mode unshaded`.** Иначе `PointLight2D` осветят сам оверлей.
3. **Коррекция на aspect.** Без неё виньетка на 16:9 — эллипс, сплюснутый по вертикали. `u_aspect` обновляется по `Window.size_changed` (см. `weather_view.gd`), потому что проектный stretch = `expand`: на Steam Deck 1280×800 aspect другой, чем на 1920×1080.

### Молния

Не отдельная нода — тот же шейдер виньетки, uniform `u_flash`. `Tween` гонит 0 → 0.75 за 0.05 с, затем 0.75 → 0 за 0.22 с. Интервал между вспышками 6–18 с случайно.

Вспышки — **визуальный** рандом, `RandomNumberGenerator.randomize()`, а не `SimRNG`. `SimRNG` — только для симуляции (docs/00 §16); заводить визуальный рандом в sim-состояние значит ломать детерминизм ради того, что на него не влияет. Зафиксировать комментарием `# РЕШЕНИЕ:`.

## 3. Частицы: где они реально нужны

Бюджет из промпта — «1–2 системы на экран». Расклад:

| Эффект | Тип | Когда | Бюджет |
|---|---|---|---|
| **Брызги прихода воды на ярус** | `GPUParticles2D`, `one_shot`, пул из 4 | кромка пересекла отметку на подъёме в `HIGH` | `amount = 24`, `explosiveness = 1.0` |
| **Пар от горна** | `GPUParticles2D`, непрерывно | горн работает (`production` активна) | `amount = 12` |
| Дождь | — | — | шейдер, не частицы |

Суммарно ≤ 3 активных эмиттера. Практический ориентир (⚠️ **НЕ ПОДТВЕРЖДЕНО**, инженерная оценка, а не число из документации): узкое место на среднем Android — **количество нод-эмиттеров**, а не частиц; держаться ≤12–16 эмиттеров и ~1000–1500 живых частиц. Мы сильно ниже.

### API one-shot burst (точный, 4.7)

```gdscript
burst.one_shot = true          # default false
burst.emitting = false         # default true
burst.amount = 24              # default 8
burst.explosiveness = 1.0      # default 0.0; 1.0 = все разом
burst.local_coords = false     # default false
burst.fixed_fps = 30           # default 30 — совпадает с нашим нижним таргетом
burst.interpolate = true       # default true

func fire(at: Vector2) -> void:
	burst.global_position = at
	burst.restart()            # restart(keep_seed: bool = false)
	burst.emitting = true
```

- `restart()` сбрасывает живые частицы; голое `emitting = true` при `one_shot` стартует цикл, но не сбрасывает. Для пула — всегда `restart()`.
- Сигнал **`finished`** — возвращать эмиттер в пул по нему, а не по `Timer`.
- **Пул, а не создание на лету.** Создавать `GPUParticles2D` на каждое событие — аллокация + GPU-буфер. `weather_view.gd` держит 4 эмиттера и берёт свободный.

### `amount_ratio` — не инструмент оптимизации

Есть в 4.7 (`float`, default `1.0`, добавлен в 4.2), **у `CPUParticles2D` его нет**. Документация прямо предупреждает: снижение `amount_ratio` **не даёт выигрыша в производительности** — буферы аллоцируются под полный `amount`. Это инструмент плавного затухания, не LOD.

Для тиров качества менять **`amount`** (пересоздаёт буфер — не каждый кадр):
```gdscript
func apply_quality(tier: int) -> void:   # 0 = слабый Android, 2 = Deck
	for p: GPUParticles2D in get_tree().get_nodes_in_group(&"fx"):
		p.amount = [8, 24, 48][tier]
```

### GPU или CPU?

- Steam Deck — `GPUParticles2D` без вопросов.
- Средний Android — тоже работает; каждый эмиттер = draw call + process-dispatch.
- Для 1–2 крошечных эффектов (`amount = 8`) `CPUParticles2D` дешевле: нет накладных расходов на GPU-буфер. Для >200 частиц выигрывает GPU.

**Решение:** брызги и пар — `GPUParticles2D` (их мало и они заметные).

## 4. Частицы и пауза — важная ловушка

Частицы симулируются на GPU и **не подчиняются паузе автоматически** — узел лишь перестаёт получать `_process`. И `sim_time` их не остановит: они анимируются движком, а не шейдером.

**`speed_scale = 0` НЕ работает надёжно** — issue #77916 (open): не останавливает и даёт артефакты при `damping != 0`. Смежные баги: #85213 (trails продолжают симуляцию на паузе), #65390 (дёрганье при паузе с `interpolate`), #83258.

**Надёжный паттерн** (реализован в `weather_view.gd`):
```gdscript
func _on_speed_changed(mult: int) -> void:
	var mode: Node.ProcessMode = Node.PROCESS_MODE_DISABLED if mult == 0 \
		else Node.PROCESS_MODE_INHERIT
	for n: Node in get_tree().get_nodes_in_group(&"fx"):
		n.process_mode = mode
		if mult > 0 and n is GPUParticles2D:
			(n as GPUParticles2D).speed_scale = float(mult)
```
То есть: **пауза → `PROCESS_MODE_DISABLED`; скорости ×1/×2/×3 → `speed_scale`** (на ненулевых значениях артефактов нет).

Все эмиттеры кладутся в группу `&"fx"` — иначе перечислять их придётся вручную.

Если при паузе всё-таки видно дрожание — обход из issue-тредов: `interpolate = false`, `fixed_fps = 0`. ⚠️ **НЕ ПОДТВЕРЖДЕНО**, что #85213/#77916 закрыты в 4.7 — проверить на своём билде.

## 5. ⚠️ Ломающее изменение 4.7: угловая скорость частиц

Issue **#115547** / PR **#117861** (milestone 4.7): положительная `angular_velocity` вращала частицы **против** часовой стрелки вопреки документации; кривые angular velocity давали кратковременное обратное вращение. Исправлено в 4.7.

**Что это значит для нас:** проект начинается сразу на 4.7, поэтому мигрировать нечего. Но если кто-то возьмёт готовый `ParticleProcessMaterial` из туториала/Asset Library, написанного под 4.5–4.6, **вращение частиц пойдёт в другую сторону**. Проверять каждый материал с ненулевым `angular_velocity_min/max`.

## 6. Хук брызг: где именно его дёргать

`WaterView` знает уровень воды каждый кадр. Брызги нужны в момент, когда кромка **пересекает отметку яруса на подъёме**:

```gdscript
var mark_now: int = floori(_level_shown)
if mark_now > _last_splash_mark and _rising:
	_last_splash_mark = mark_now
	weather.splash_at(Vector2(_camera_center_x, (TOP_MARK - float(mark_now)) * PX_PER_MARK))
```

Это даёт 6 всплесков за подъём `HIGH` (от −6 до 0) — по одному на ярус, ровно как в промпте («брызги в момент прихода воды на ярус»). На спаде `EBB` брызг нет.

Звук на это же событие — этап 17 уже требует «брызги прихода воды» в маппинге docs/00 §15. Значит sim-события для этого либо уже есть, либо звук тоже вешается на этот визуальный хук — согласовать с тем, как сделан `AudioService`.

## 7. Приёмка

- [ ] В ясный цикл дождь не рисует ничего (проверить в Visual Profiler: оверлей не даёт фрагментов).
- [ ] Шторм: дождь и виньетка нарастают ~3 с, а не появляются рывком.
- [ ] Молнии идут с интервалом 6–18 с, вспышка короткая (<0.3 с).
- [ ] Виньетка круглая на 1280×720, 1280×800 и 1920×1080 (aspect корректируется).
- [ ] Банер кризиса читаем поверх виньетки.
- [ ] На паузе: дождь стоит, брызги стоят, пар стоит.
- [ ] На ×3: брызги и пар ускорены втрое.
- [ ] Подъём `HIGH`: ровно 6 всплесков, по одному на ярус.
