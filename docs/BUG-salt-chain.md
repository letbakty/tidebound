# Дефект: соляная цепочка производит ровно один раз за забег

Статус: **локализован, не исправлен.** Найден при разборе падения `test_production/test_salt_chain` после починки `buffer_take`.

## Симптом

Тест ожидает ≥10 провизии к концу третьего цикла, получает 4.

## Что уже исправлено

`sim/building_system.gd:246`, функция `buffer_take`. Было:

```gdscript
var order: Array[String] = [item_id] if dry_only \
	else [StackUtil.buffer_key(item_id, true), item_id]
```

Тернарный оператор возвращает нетипизированный `Array`, присваивание в `Array[String]` падает в рантайме. Функция прерывалась **на каждом вызове** — материалы из буферов станций не списывались, станции работали «бесплатно». В логе прогона это давало **365 `SCRIPT ERROR`**, при том что все тесты были зелёными: раннер проверяет только свои `check()`, а `SCRIPT ERROR` для него невидим.

Заменено обычным `if` (единственное такое место в проекте — проверено грепом). После фикса: **0 ошибок**, но `test_salt_chain` начал честно падать, потому что раньше проходил на сломанном поведении.

## Что осталось

Замеры (испаритель на −1 x=14, солильня на +3 x=4, склад с 20 `catch` и 20 `freshwater`, `SUPPLY=3`, сид 4242):

| Момент | Соль на складе | Провизия | Буфер солильни |
|---|---|---|---|
| т1949 (конец LOW, цикл 1) | 0 | 8 | `{catch: 2, freshwater: 1}` |
| т1960 (сразу после) | **1** | 8 | `{catch: 2, freshwater: 1}` |
| т2249 | 0 | **10** | `{freshwater: 1}` |
| т2999 | 0 | 10 | `{catch: 2, freshwater: 1}` |
| т4940–5100 (весь переход LOW→SIGNAL цикла 2, шаг 20) | **0 всегда** | 10 | `{catch: 2, freshwater: 1}`, `pending=[]`, причина `no_materials` |
| т5999, т7949 | 0 | 9 → 5 | то же |

Первый цикл отрабатывает штатно: испаритель даёт соль, агент довозит, солильня крафтит, провизия 8→10. **Начиная со второго цикла соль на складе не появляется вообще.**

## Ключевое наблюдение

В **изолированном** сценарии (тот же испаритель, та же позиция, без солильни и без агентской активности) соль производится каждый цикл и накапливается:

| Тик | Фаза | `flooded` | `flooded_in_phase` | `is_working` | Соль |
|---|---|---|---|---|---|
| 1948 | LOW | false | false | true | 0 |
| 2600 | HIGH | true | true | true | **1** |
| 4948 | LOW | false | false | true | 1 |
| 5600 | HIGH | true | true | true | **2** |
| 7948 | LOW | false | false | true | 2 |

Флаги корректны, `_passive_allowed` пропускает, `on_phase_started` сбрасывает вовремя, порядок в `SimWorld.tick()` (`production.on_phase_ended` → `buildings.on_phase_started`) верный.

**Значит производство соли ломает не сам испаритель, а взаимодействие с остальными системами** — присутствие солильни, агентской активности или обеих. Это и есть точка, с которой надо продолжать.

## Что проверить дальше

1. Замерить `flooded_in_phase`, `is_working` и `idle_reason` **самого испарителя** в сценарии с солильней — тот же замер, что в таблице выше, но в полном окружении. Если флаги там отличаются, причина в них.
2. Проверить `_produced_cycle` и `_output`: не уходит ли соль в `spill` на землю (испаритель на −1, землю там затапливает каждый цикл) при заполненном ближайшем складе. `_output` выбирает ближайший склад **по расстоянию**, а не первый попавшийся.
3. Проверить `has_space("salt", 1)` для склада с 7+ занятыми слотами из 12.

## Урок для этапа 19

Раннер обязан валить прогон при появлении `SCRIPT ERROR`, а не только при провале `check()`. Иначе дефекты такого класса копятся незаметно: 365 ошибок за прогон при полностью зелёном отчёте.
